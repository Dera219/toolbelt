# ToolBelt — Architecture

> Working codename. Run a trademark / app-store / domain search before public launch.

**One-liner:** An on-demand marketplace that connects customers with vetted blue-collar
workers (plumbers, electricians, movers, cleaners, handymen, painters, HVAC techs) the
way Uber connects riders with drivers.

---

## 1. Product thesis

Uber won because it collapsed three frictions: **discovery** (find someone now),
**trust** (ratings + identity), and **payment** (cashless, escrowed). Blue-collar work
still has all three frictions in most of the world. ToolBelt collapses them for local
trades.

**What we are NOT building first:** scheduling software for contractors (Jobber),
lead-gen ads (Thumbtack's old model), or a labor staffing agency. We are building a
**two-sided, transaction-taking marketplace**: customer posts a job → nearby qualified
workers bid or accept → work happens → payment clears through us → both sides rate.

### Personas
| Persona | Needs | Success metric |
|---|---|---|
| **Customer** | Fast match, upfront price, trust that the stranger is legit | Time-to-first-offer < 15 min |
| **Worker** | Steady job flow, fast payout, low take-rate, no lead fees | Jobs/week, payout latency |
| **Ops/Admin** (us) | Vetting queue, dispute resolution, fraud monitoring | Dispute rate < 2% |

### Core loop
```
post job → match/notify nearby workers → offers → accept →
work (status tracking) → complete → capture payment → payout → mutual rating
```

---

## 2. System architecture

### Stage 1 (now → first 10k users): Modular monolith
One deployable FastAPI service, internally split into modules with strict boundaries.
Do **not** start with microservices — a solo/small team cannot pay the operational tax,
and module boundaries give us the seams to split later.

```
                        ┌─────────────────────────────┐
  Expo mobile app ───►  │        FastAPI monolith      │ ───► PostgreSQL + PostGIS
  (customer + worker)   │  auth │ users │ jobs │ offers│ ───► Redis (cache, queues,
  Next.js admin ─────►  │  match │ payments │ ratings  │        rate limits)
                        │  notifications │ disputes    │ ───► S3-compatible storage
                        └─────────────────────────────┘        (photos, documents)
                                     │
                          background workers (arq/Celery):
                          notification fan-out, payout jobs,
                          document-verification callbacks
```

**Module boundaries (enforced by package structure, later by service split):**
- `identity` — accounts, sessions, KYC/vetting state
- `catalog` — trades taxonomy, service areas, pricing guidance
- `jobs` — job lifecycle state machine, offers, assignment
- `matching` — geo search, ranking, notification fan-out
- `payments` — escrow, capture, payouts, refunds (wraps Stripe Connect)
- `reputation` — ratings, reviews, completion stats
- `trust` — disputes, reports, fraud signals, admin actions

### Stage 2 (scale triggers, split only when a trigger fires)
- Matching fan-out saturates the API → extract `matching` behind a queue.
- Payment compliance (PCI scope, audits) → extract `payments`.
- Real-time location tracking ("worker en route") → dedicated WebSocket gateway.

### Clients
- **Mobile (primary): Expo / React Native, one codebase, two role-modes** (customer
  mode / worker mode in one app — Uber-style separate apps only after PMF).
- **Admin: Next.js** internal dashboard (vetting queue, disputes, fraud review).
- **API contract: OpenAPI** generated by FastAPI → typed client generated for the app.

## 3. Domain model (v1)

```
User            id, email, phone, password_hash, role∈{customer,worker,both},
                locale, currency, status∈{active,suspended,deleted}, created_at
WorkerProfile   user_id, trade(s), bio, hourly_rate_cents, base_lat, base_lng,
                service_radius_km, is_available, vetting_status∈{unverified,
                pending,verified,rejected}, rating_avg, jobs_completed
Job             id, customer_id, trade, title, description, photos[],
                lat, lng, address_text, scheduled_for (nullable = ASAP),
                budget_cents (nullable = open to offers), currency,
                status∈{open,assigned,in_progress,completed,cancelled,disputed},
                assigned_worker_id, created_at
Offer           id, job_id, worker_id, price_cents, message,
                status∈{pending,accepted,declined,withdrawn,expired}
Payment         id, job_id, amount_cents, platform_fee_cents, currency,
                provider_ref, status∈{authorized,captured,refunded,paid_out}
Rating          id, job_id, rater_id, ratee_id, stars(1–5), comment
Dispute         id, job_id, opened_by, reason, status, resolution
```

**Job state machine (single source of truth, enforced in one place):**
```
open ──accept offer──► assigned ──worker starts──► in_progress ──both confirm──► completed
  │                        │                            │
  └─cancel (customer)      └─cancel (either, w/ fee     └─dispute──► disputed ──► resolved
                              rules after cutoff)
```
Every transition writes an immutable `job_events` audit row (who, what, when, from→to).

**Invariants (enforced at the service layer, tested):**
- Money is always integer minor units (`cents`) + ISO-4217 currency. Never floats.
- One accepted offer per job; accepting one atomically expires siblings.
- A worker cannot offer on their own job; a customer can only rate their own jobs.
- Status transitions only through the state machine — no direct status writes.

## 4. Matching & geo

- **MVP:** candidate workers = same trade, available, verified, within
  `min(job↔worker distance, worker.service_radius_km)`. Haversine on indexed
  bounding-box prefilter. Ranking: distance + rating + acceptance rate + recency.
- **Scale:** PostGIS `geography` columns + GiST index (`ST_DWithin`), then optional
  H3 cells for fan-out sharding. The query lives behind `matching.find_candidates()`
  so the implementation can swap without touching callers.
- **Notification fan-out:** push to top-N candidates in waves (5 workers, 90s, next
  wave) — prevents offer-storms and gives closer/better workers first shot.

## 5. Payments (the part that makes it a business)

- **Stripe Connect (Express accounts)** — one integration that handles worker
  onboarding/KYC, card processing, escrow-like capture flow, payouts, and 1099/tax
  forms in supported countries. Do not build custom escrow; that's a money-transmitter
  license problem.
- Flow: accept offer → **authorize** customer card → job completed → **capture** →
  platform fee (target 15–20%) retained → **payout** to worker (instant payout as a
  premium feature later).
- Every provider webhook is idempotent (store `event_id`, process once).
- **Internal double-entry ledger** from the first real transaction: every money
  movement (authorize, capture, fee, payout, refund, adjustment) is a balanced pair
  of immutable ledger entries; account balances are *derived*, never stored-and-
  mutated. Uber and Airbnb both had to retrofit this painfully — Stripe's provider
  truth is not a substitute for our own books (disputes, reconciliation, audits).
- **Provider-call journal** — the other half of the ledger. The ledger records what
  money *did*; `provider_calls` records what we *asked the provider to do*, written
  and committed on its own connection *before* the call. It exists because a provider
  call is an irreversible external effect made from inside a database transaction that
  is not yet durable: capture, transfer, refund and reversal all execute before their
  local rows are written, so a failure later in the same transaction rolls the database
  back while the money has already moved, and the retry — with no memory of the first
  attempt — pays twice. Every money movement goes through one helper
  (`payments/journal.py`), every provider method requires an idempotency key, and a key
  that comes back with different parameters is refused rather than sent. Provider keys
  alone are not enough: Stripe prunes them after 24 hours and then treats a reuse as a
  new request, so the local record is what makes a next-morning repair safe.
- **Reconciliation sweeper** (`payments/reconcile.py`) — what closes the journal's one
  admitted gap. A crash between the provider call and the completion write leaves a row
  `pending`, and the journal is honest that this means "outcome unknown"; until the
  sweeper existed, nothing ever asked the provider, so `pending` meant unknown
  *permanently*. Its job is to tell **"nothing happened"** apart from **"I cannot
  tell"** — the same word in the journal, and completely different operationally: one is
  a job that silently never got paid, the other is money sitting somewhere nobody is
  looking. Three verdicts, and `unknown` is a real answer rather than a failure.
  - **Read-only, never a replay.** The shortcut — re-issue the request under its
    original idempotency key, which inside Stripe's 24-hour window returns the original
    object — has a hole the size of the problem: a replay returns the original object
    only *if the key was consumed*, and whether it was consumed is exactly the question.
    If the request never reached Stripe, the replay creates a brand new charge — the
    sweeper causing the movement it was sent to investigate, in precisely the case it
    exists to detect. So one path, both windows, all reads.
  - **Attribution by fingerprint.** For refunds, transfers, reversals and authorizes
    the object was created by the call whose reference we lost, so it is identified by
    content: candidates are pulled from the provider, the call parameters are rebuilt
    from each, and the one hashing to the `request_fingerprint` written *before* the
    call is ours. Already-claimed references are excluded first, since two refunds of
    the same amount on the same charge fingerprint identically. Exactly one match
    resolves; zero means it never landed; more than one is the double-spend itself and
    is reported, not resolved.
  - **Knowledge gap, never money gap.** It may relabel a journal row and record the true
    reference. It never refunds, transfers, captures or reverses, never edits a Payment,
    never writes a ledger entry. Disagreements between the provider and our books are
    reported as discrepancies for a human. Enforced structurally: the provider is
    wrapped in a read-only guard that raises on any money method. A sweeper that
    silently repairs money state is a second class of bug wearing the costume of a fix.
  - Runs from `api/scripts/reconcile_provider_calls.py` (dry-run by default) and from
    `POST /admin/payments/reconcile`, both through the same service function so the
    scheduled run and the by-hand run cannot drift. **No scheduler in-process** — a
    background thread in a free-tier web service is a new failure mode, not a feature.
    Operating instructions and how to read each outcome: DEPLOY.md.
- Cash-market countries (later): "record cash payment, collect fee from worker
  balance" mode — this is how Uber cracked cash markets.

## 6. Trust & safety (non-negotiable for this vertical)

- **Worker vetting ladder:** email/phone verify → government-ID + selfie match (via
  provider: Stripe Identity / Persona) → license upload for regulated trades
  (electrician, HVAC, plumbing where required) → background check (Checkr or local
  equivalent) where legally available. Vetting status is public on the profile.
- **In-app chat only until job accepted** (masked contact info) — protects both sides
  and protects the take-rate from disintermediation.
- Double-blind ratings (revealed after both submit or 14 days).
- Dispute flow with photo evidence, admin queue, partial-refund tooling.
- Insurance: start with clear ToS liability boundaries; add per-job insurance
  partner (e.g. bunker/Thimble-style) as a differentiator later.

## 7. International-quality bar (day-one decisions that make going global cheap)

- **i18n from day one:** all user-facing strings through a translation layer
  (`react-i18next` in app, message catalogs server-side); no concatenated sentences.
- **Currency-aware money type** everywhere (minor units + currency code).
- **Phone-first auth** (E.164 normalized) — email optional; much of the target
  workforce worldwide is phone-primary.
- **Trades taxonomy is data, not code** — per-country trade lists and licensing rules
  live in the `catalog` module's tables.
- UTC timestamps in storage, locale/timezone formatting at the edge.
- Address as free text + lat/lng (structured address schemas break internationally).

## 8. Tech stack & rationale

| Layer | Choice | Why |
|---|---|---|
| API | FastAPI + Pydantic v2 | Team already ships FastAPI (TradeDesk); async, OpenAPI for free |
| DB | PostgreSQL 16 + PostGIS | Geo queries, transactional integrity for money/state |
| ORM/migrations | SQLAlchemy 2.0 + Alembic | Boring, proven |
| Cache/queue | Redis + arq | Fan-out, rate limiting, background jobs |
| Mobile | Expo (React Native) + TypeScript | One codebase, OTA updates, fastest path to both stores |
| Admin | Next.js | Fast internal tooling |
| Payments | Stripe Connect Express | KYC + escrow-flow + payouts without a money license |
| Identity/vetting | Stripe Identity / Persona + Checkr | Buy, don't build |
| Push | Expo Push → FCM/APNs | Free tier, simple |
| Auth | JWT access (15 min) + rotating refresh tokens; bcrypt password hashing; SMS OTP for phone verify | Standard, revocable |
| Hosting | Fly.io or Railway → AWS later | Cheap start, Postgres included, easy multi-region later |
| Observability | Sentry + structured JSON logs → Grafana Cloud | Errors first, dashboards second |
| CI | GitHub Actions: lint (ruff), typecheck (mypy/tsc), tests, migration check | Merge = deployable |

## 9. Security checklist (enforced in code review + CI)

- Argon2/bcrypt password hashes; JWT with short expiry + refresh rotation.
- All money/state mutations in DB transactions with row locks on the job.
- Idempotency keys on payment-touching endpoints.
- Rate limiting (Redis) on auth + offer endpoints; account lockout with backoff.
- Object-level authorization on **every** endpoint (customer sees own jobs; worker
  sees open jobs + own offers) — tested, not assumed.
- PII: encrypted at rest (DB-level), masked in logs, deletion workflow (GDPR/CCPA).
- Webhook signature verification (Stripe) + idempotent processing.

## 10. Roadmap

| Phase | Scope | Exit criterion |
|---|---|---|
| **0 — Core API** (now) | Auth, worker profiles, job post, nearby search, offers, accept flow, state machine, tests | Full loop passes in tests |
| **1 — Trust MVP** | Ratings, phone OTP, vetting states, admin endpoints, in-app chat | A stranger would plausibly hire through it |
| **2 — Money** | Stripe Connect: authorize/capture/payout, fees, refunds, webhooks | Real $1 test transaction end-to-end |
| **3 — Mobile app** | Expo app: both role-modes, push notifications, photo upload | TestFlight/Play internal build |
| **4 — Pilot launch** | One city, 1–3 trades (cleaning/handyman/moving are unlicensed → start there), manual worker onboarding, ops dashboard | 100 completed paid jobs |
| **5 — Scale & i18n** | PostGIS, wave fan-out, second market, second language, cash mode | Second city profitable per-job |

**Strategy note:** launch with *unlicensed* trades (cleaning, moving, handyman,
assembly, yard work) in **one** dense city. Licensed trades (electrical, plumbing,
HVAC) come after the licensing-verification pipeline exists. Marketplaces die from
being thin everywhere instead of liquid somewhere.

## 11. Platform pillars (what the incumbents have that we schedule, not skip)

Benchmarked against Uber, DoorDash, TaskRabbit, and Thumbtack. Each pillar has a
build trigger — building it earlier is cargo-culting, later is a scramble.

**Event backbone.** All state changes emit domain events (`job.posted`,
`offer.accepted`, `job.completed`…) via a **transactional outbox** (events written
in the same DB transaction as the state change, relayed to Redis Streams → Kafka
later). This is how notifications, analytics, and ML features consume the system
without coupling to it. *Trigger: Phase 1, when notifications ship — the `job_events`
audit table is already the seed of this.*

**Data & metrics.** Nightly export → DuckDB/BigQuery. The marketplace lives or dies
by liquidity metrics, watched from the first pilot week: time-to-first-offer, fill
rate (% jobs completed), worker utilization, take-rate realized, retention cohorts,
supply/demand ratio per zone. *Trigger: Phase 4 pilot — before spending $1 on
acquisition.* Experimentation platform (Uber XP-style): post-PMF only.

**Reliability & operations.** SLOs once real users depend on us: 99.9% API
availability, p95 < 300ms on search, < 60s notification latency. Error budgets gate
feature work vs. hardening. Postgres PITR backups + restore drills. Graceful
degradation order: matching can be stale before job state can be wrong, and job
state can be stale before money can be wrong. *Trigger: Phase 4.*

**API conventions (day one, cheap now / expensive later).**
- **Pagination on every list endpoint** (`limit` capped server-side; cursor
  pagination when feeds get long) — unbounded lists are how APIs fall over.
- **Idempotency keys** accepted on mutating endpoints; mandatory on all
  payment-touching endpoints in Phase 2 (mobile networks retry; money must not).
- **API versioning (`/v1`) before the first app-store release** — you cannot force
  mobile clients to update, so every shipped contract is frozen the day it ships.

## 12. Market reality — who died here, who won, and our counters

This category is both a graveyard and a proven market. Ignoring the graveyard is
how you join it.

| Company | Outcome | Killer |
|---|---|---|
| **Homejoy** (cleaning, $38M raised) | Dead 2015 | Leakage (customers rebooked cleaners off-platform), discount-driven CAC that never paid back, 1099-classification lawsuits |
| **Zaarly** | Dead 2020 | Too broad, no liquidity anywhere |
| **Takl** | Dead | Thin two-sided liquidity outside launch metro |
| **Amazon Home Services** | Wound down | Episodic demand, no supply loyalty — even Amazon couldn't brute-force it |
| **Handy** | Distressed sale to ANGI | Worker churn, quality variance, classification suits |
| **TaskRabbit** | Modest exit (IKEA) | Survived by narrowing to assembly/moving-adjacent tasks |
| **Thumbtack** | Alive, pivoted hard | Lead-gen model burned pros (pay for leads, not jobs) — we deliberately take fees on *completed jobs only* |
| **Urban Company** (India) | **Won — IPO 2025** | Full-stack: trained pros, standardized kits, supplies included, strong repeat categories |
| **Instawork / Wonolo** | Alive and growing | Blue-collar *shift* marketplaces — businesses, not consumers, as demand side |

**The five known killers and our counters:**
1. **Leakage** (the #1 killer): after job one, both sides want to cut out the fee.
   Counters: masked contact until acceptance, in-app chat, payment protection +
   dispute rights only on-platform, rebooking shortcuts, worker perks (instant
   payout) tied to platform volume. Accept that some leakage always happens;
   price the take-rate for it.
2. **Low frequency**: a mover is needed twice a decade. Counter: anchor on
   **cleaning** (weekly/biweekly recurring — the only home-services vertical with
   subscription-like frequency), let episodic trades ride on that liquidity.
3. **Classification risk**: don't control schedules, don't set mandatory rates,
   don't provide uniforms/training that imply employment; workers set prices via
   offers (already our model). Legal review per market before launch.
4. **Thin liquidity**: one city until fill-rate > 80% and time-to-first-offer
   < 15 min. Density beats coverage.
5. **The equipment & materials problem** (real, and mostly ignored by the dead
   companies): many gig cleaners lack supplies/transport; repair jobs (plumbing,
   electrical) can't be priced sight-unseen because parts are unknown; movers
   split into labor-only vs. truck-included. Product counters, built into v1:
   - Worker profile declares **has_own_tools / has_vehicle**; jobs declare
     **customer_provides_supplies**; matching and search respect them.
   - Repair trades (Phase 2+): **diagnostic-visit flow** — small fixed callout fee,
     then an in-app revised quote with a materials line item, customer approves
     before work continues. Never pretend a plumbing job is an Uber ride.
   - Urban Company's standardized-kit model (platform-supplied consumables) is the
     Phase 5 answer for cleaning quality variance in dense markets.
